## aerowow (bootstrap + Dev 1 — Счета)
### Что делал / какие агенты и субагенты
Пять сессий, логи — `sessions/aerowow/`:

1. **Bootstrap** (28.08) — структура репозитория, процессные документы, branch
   protection; без кода. Главная сессия + 1 Plan-субагент (формат pbxproj с
   synchronized folders, дизайн контракта, команды gh); часть его результата —
   готовый Swift-код контракта и заглушек — отброшена решением команды.
2. **Core-контракт** (28.08) — модели, WalletStore, MoneyFormatter, моки.
   Subagent-driven: план от контроллер-агента (skill `writing-plans`), затем на
   каждую из 4 задач свежая пара «имплементер (haiku) + ревьюер (sonnet)», строго
   последовательно; плюс 2 fix-раунда по находкам ревью и 2 повторных
   scoped-ревью. TDD через swiftc-харнесс в некоммитируемой `tmp-tests/` —
   48 assertions, включая конкурентный тест гонки ключа идемпотентности.
3. **Оболочка core/shell** (28.08) — TabView, роутер, стабы. Задача 6:
   имплементер (haiku) + ревьюер (sonnet), ревью чистое с первого раза; задача 7
   (смоук на симуляторе через `simctl`, README, PR) — 1 субагент по брифу.
4. **PDF-макеты + iOS 26.0** (28.08) — субагенты сознательно не запускались: обе
   правки мелкие и проверяются детерминированно (grep + `xcodebuild`). Отдельный
   worktree.
5. **Экран «Счета»** (29.08) — обязательный пункт ДЗ: экран раздроблен на 3 части
   и реализован 3 параллельными сабагентами через Workflow, каждый в своём git
   worktree (ветки `feature/accounts-sub{1,2,3}`), каждому — только свои файлы.
   До них — 2 Explore (параллельно) + 1 Plan; после мержа трёх веток — ревью-
   Workflow из 13 агентов (3 параллельные линзы-ревьюера + 10 адверсариальных
   верификаторов, по одному на находку; ~727k токенов, ~7 минут). Итог ревью:
   10 подтверждённых находок, 0 отклонённых верификацией.

Итого ~35 запусков субагентов (считая fix-раунды и повторные ревью отдельными
запусками): из них параллельно — 2 Explore, 3 имплементера экрана и ревью-workflow
из 13 агентов; остальные — последовательно (subagent-driven пары Core).

### Что не сработало
- Первый план бутстрапа: агент собирался написать весь каркас кода (контракт,
  стор, мок-данные, вью-заглушки) и рукописный `project.pbxproj` — отброшено,
  команда решила писать код сама, проект создать в Xcode GUI. Урок: сначала
  фиксировать границы «что делает агент / что делают люди», потом просить план.
- Механика Xcode-проекта дала три сюрприза: `.gitkeep` в папках фич ломали
  сборку («Multiple commands produce .gitkeep» — синхронизированные папки
  копируют их в бандл); схема не была расшарена — на свежем клоне
  `xcodebuild -scheme` падал, а галочка Shared с первого раза не сохранилась;
  Xcode создал вложенный git-репозиторий, попавший в коммит пустой
  gitlink-ссылкой (вложенный `.git` удалён, папка переподключена).
- Код из исходного плана Core содержал два бага, которые нашли только
  субагенты-ревьюеры: округление денег через двоичный double внутри
  `NumberFormatter` (`Decimal("1.005")` → «1,00»; исправлено `NSDecimalRound`,
  коммит `57b0869`) и TOCTOU-гонку ключа идемпотентности — `MainActor`
  реентерабелен на `await Task.sleep`, два одновременных `transfer` с одним
  ключом проходили проверку реестра оба (исправлено повторной проверкой после
  паузы + конкурентный тест, коммит `6981e9b`).
- Скрипт скилла task-brief не понял русские заголовки задач («### Задача N») —
  брифы для субагентов вытаскивались вручную через `awk`.
- Фолбэк-команда выбора симулятора из брифа вернула первый попавшийся iPhone 14,
  для которого не было валидного destination схемы — UDID подбирался вручную
  (iPhone 17, iOS 26.2), команду из брифа один в один выполнить не удалось.
  Смоук оболочки прошёл только headless-скриншотом, без ручного прогона человеком.
- Гипотеза собственного лога бутстрапа («target 26.5, соберут только с
  Xcode 26.5+») не подтвердилась: 26.5 стоял лишь в project-level конфигурациях,
  target-level уже был 26.0 и перекрывал проект. Риск для проверяющих был меньше
  заявленного; правку довели до конца, потому что расхождение вводило в
  заблуждение в UI Xcode.
- `Read` не рендерит PDF («pdftoppm is not installed») — макеты сверялись через
  штатный `qlmanage`. Сами макеты не покрывают все состояния из ТЗ: на
  `accountsDesign` нет сноски про валютный счёт, на `historyDesign` — поиска и
  части фильтров-чипов.
- Plan-агент экрана «Счета» упал на середине из-за ухода машины в сон —
  возобновлён продолжением диалога (SendMessage) с того же места, без
  перезапуска с нуля.
- MCP-инструменты Context7 не попали в сессию (сервер подключён в конфиг, но
  сессия стартовала раньше) — обойдено публичным HTTP API через WebFetch,
  функционально равнозначно.
- `README.md` ссылается на несуществующий `docs/MiniWallet-specs.pdf` —
  устаревшая ссылка замечена, но не починена: файл вне зоны владения Dev 1.
- Три параллельных сабагента сдали зелёную сборку, но ревью-workflow подтвердил
  10 реальных проблем: от будущего redeclaration (`PrimaryButton` — все Features
  компилируются в один модуль, одноимённый тип у Dev 2/3 сломал бы сборку только
  после мержа обеих веток) до фактического зазора 36pt вместо 12pt из-за
  `Spacer(minLength:)` внутри HStack со spacing. Зелёная сборка ≠ чистый код.

## PM — ТЗ и PDF
### Что делал / какие агенты и субагенты
Три ТЗ (`docs/specs/01-accounts.md`, `02-transfer.md`, `03-history.md`) собраны из
`design/pen-dev-prompt.md` по шаблону `docs/specs/TEMPLATE.md`, критерии приёмки — в форме
«дано/когда/тогда». Главная сессия Claude Code писала черновики; по каждому ТЗ отдельно
запрашивался разбор «что дословно из источника / что добавлено для ясности / что агент
решил сам» — третий список разбирался PM по пунктам, решения принимал человек.
Ревью — три независимых read-only субагента, по одному на файл, каждому только его ТЗ,
шаблон, `CLAUDE.md`, дизайн-промпт и ответы разработчиков по его разделу; выводы друг
друга агенты не видели. Отчёты сведены, дубли сняты, замечания разложены на критичные,
средние и необязательные, отдельно выписаны отклонённые. Workflow —
`workflows/jwynana-spec-from-design.md`, лог — `sessions/jwynana/2026-08-28-specs.md`.

### Что не сработало
- Агент писал ТЗ, принимая продуктовые решения за PM: только по экрану «Счета»
  таких самостоятельных допущений набралось 13 — от «приложение открывается на этой
  вкладке» до придуманного текста сноски. Помог явный разбор по трём спискам;
  без него они бы ушли в разработку как согласованные требования.
- Первые версии ТЗ фиксировали техническую реализацию (сигнатуры методов, имена типов,
  где вычисляется сводный баланс). Пришлось переписывать разделы «Данные из общего
  контракта» в «данные и возможности» + «вопросы к разработчикам».
- Три вызова субагентов ушли в двух сообщениях, поэтому прогон оказался частично
  последовательным: параллельно пересеклись только Transfer и History. Параллельность
  даёт батч в одном сообщении, а не порядок вызовов.
- Субагенты предлагали упростить осознанные решения PM (правила поиска, механизмы
  сброса фильтров, счётчик) — такие замечания отклонены с обоснованием.
- Зато ревью нашло реальную дыру: при принятой механике ключа состояние
  «Перевод уже выполнен» было недостижимо из UI, то есть идемпотентность —
  главная механика ДЗ — не воспроизводилась ни одним действием пользователя.

### aerowow — worktrees и изоляция с выводом отказа

В логах фигурируют минимум 5 git worktree:

- 1 × воркитри с веткой `core/shell` — упомянут в логе design-and-ios26 как
  занятый открытым на тот момент PR.
- 1 × `chore/design-pdfs-and-ios26` — изоляция мелких правок (нативный
  `EnterWorktree` + skill `using-git-worktrees`): в воркитри `core/shell`
  правки попали бы в чужой дифф.
- 3 × `.claude/worktrees/accounts-sub{1,2,3}` — по одному на параллельного
  сабагента экрана «Счета» (ветки `feature/accounts-sub{1,2,3}` от общего
  prep-коммита с дизайн-токенами). Каждый сабагент собирал проект у себя,
  коммитил только свои файлы и не пушил; ветки мержил оркестратор.

Зафиксирован 1 реальный отказ изоляции: попытка сложить превью PDF-макетов в
scratchpad за пределами воркитри была отклонена — команда сочтена слишком
сложной для проверки границ. Обход — рендер во временную папку внутри воркитри
и ручное удаление до коммита. Вывод: изоляция действительно блокирует запись за
границы воркитри, причём проверка срабатывает и на безопасной команде, если не
может её проанализировать, — обход потребовал ручных шагов.

Инъекция на двух моделях и отдельный отчёт по инструментам не делались — следов
в логах нет, в отчёт не включены.
